## 003 — `db/proposed/003_public_indexes.sql`

### SQL exact

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_user_created
  ON public.orders (user_id, created_at DESC);
-- D3 (messages) : commenté, à ne pas exécuter avant 005
-- CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_messages_quota
--   ON public.messages (user_id, status, sent_at DESC);
```

Le fichier se termine par un `SELECT` de contrôle des index `INVALID`.

### Tables concernées

| Table             | Taille (mesurée)        | Index existants                                                                                                                                                                         |
| ----------------- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `public.orders`   | 7 155 lignes, 6,1 Mo    | pkey, `orders_user_tracking_uniq` (UNIQUE), **`orders_user_tracking_idx` (mêmes colonnes, redondant)**, `(user_id, delivery_status, last_update)`, `tracking_number`, `delivery_status` |
| `public.messages` | 532 516 lignes, ~210 Mo | pkey, `(user_id)`, `(tracking_number)`                                                                                                                                                  |

### Bénéfice

- **D4 (`orders`)** sert `countOrdersThisMonth`, appelée à chaque sync, par
  `/api/quotas/state` et par le handler de file. Il sert aussi les vues
  triées par `created_at` (branche `p1-rls-pages-via-api`). Avec environ
  7 000 lignes, le gain actuel se chiffre en **millisecondes**. Il ne devient
  réel qu'avec la croissance du nombre de tenants et de commandes.
- **D3 (`messages`)** sert le plafond anti-ban, lu **à chaque envoi**. Aujourd'hui,
  ce comptage parcourt toutes les lignes du tenant via `(user_id)` puis
  filtre `status` et `sent_at` sur la table : 493 784 lignes pour le tenant B.
  C'est le seul index de 003 au bénéfice immédiat, mais il vient **après** 005.

### Risques

1. **Coût en écriture sur le chemin chaud.** Le sync upsert **toutes** les
   commandes du tenant (≈ 5 000) à chaque passage. Aujourd'hui, la colonne
   indexée `last_update` change à chaque fois (heure du sync), donc les mises
   à jour ne sont pas HOT : chaque ligne réécrite touche **tous** les index.
   Un 7ᵉ index représente environ 5 000 insertions d'index de plus par sync,
   par onglet ouvert. Une fois la branche `p1-orders-stats-correctness`
   mergée, les lignes inchangées gardent leur `last_update` et **peuvent**
   redevenir HOT, à condition qu'il reste de la place dans la page
   (fillfactor 100 par défaut).
2. **`CONCURRENTLY` hors transaction.** Le SQL Editor envoie le script entier
   en une seule requête. Exécuter le fichier tel quel (CREATE + SELECT) échoue
   avec « cannot run inside a transaction block ». Il faut exécuter **l'instruction
   seule**.
3. **Échec en cours de création.** Il laisse un index `INVALID`. Le contrôle
   de fin de fichier le détecte, puis `DROP INDEX CONCURRENTLY`.

### Compatibilité et impact production

- Aucune contrainte n'est modifiée. L'upsert sur conflit
  `(user_id, tracking_number)` s'appuie sur `orders_user_tracking_uniq`, qui
  n'est pas touché. L'autre application n'utilise pas `orders`.
- Pendant le gel : **aucun impact**, rien n'est exécuté.

### Recommandation

- **D4** : à faire après le rapport 72 h, en heure creuse, **en même temps
  que** `DROP INDEX CONCURRENTLY orders_user_tracking_idx`. Cet index double
  exactement l'index unique, donc le nombre d'index reste constant et le coût
  d'écriture ne bouge pas. Avant de supprimer, vérifier
  `pg_stat_user_indexes.idx_scan` sur les deux index.
- **D3** : après 005 uniquement. À ce stade, la table fait 45 lignes et l'index
  devient optionnel.
- Découverte annexe : les ~5 000 upserts par sync et par onglet sont une piste
  de charge base à mesurer après la fenêtre, avec `pg_stat_user_tables.n_tup_upd`
  sur `orders` sur 1 h. Ne réécrire que les lignes modifiées est un correctif
  P2 candidat. Voir aussi la branche `p1-orders-stats-correctness`, qui donne
  à `last_update` la date ZR du changement d'état.

## 005 — `db/proposed/005_messages_cleanup.sql`

### Ce que le fichier ferait

| Étape | Action                                                            | Statut                   |
| ----- | ----------------------------------------------------------------- | ------------------------ |
| E1    | `SELECT` de comptage des lignes éligibles (lecture seule)         | autorisée (E1 = OUI)     |
| E2    | copie des lignes éligibles vers `autotim.messages_archive_202609` | commentée, « plus tard » |
| E3    | `DELETE` par lots de 10 000, puis `VACUUM (ANALYZE)`              | commentée, « plus tard » |

**Critère d'éligibilité** : `status='echec'` et `error_message LIKE
'%Session WhatsApp expirée%'` et `sent_at < now() - 30 days`.

### Pourquoi

Du 2026-04-24 au 2026-07-30, la session WhatsApp était morte. Chaque tentative
a écrit une ligne `echec` : **532 471 échecs pour 45 envois réels**, soit
~210 Mo et 42 % du quota Free de 500 Mo.

### Volume

- 532 471 lignes éligibles, soit 99,991 % de la table. 45 lignes `envoye`
  restent hors périmètre.
- Le snapshot du 2026-09-24 donne 532 516 = 532 471 + 45 : **aucune ligne
  nouvelle depuis le 2026-09-10**. Il n'y a pas eu de récidive, mais pas
  d'envoi non plus.
- Le motif `LIKE` couvre les deux libellés produits par `/api/whatsapp/send`,
  « …(Connection Closed) — reconnecte le QR » et « … — annulé (reconnecte
  d'abord) ». Ce sont deux échecs, ce qui est correct. Attention à la
  normalisation Unicode du « é » : E1 **doit** retourner ≈ 532 471. Un
  résultat nettement inférieur signifie un motif non reconnu : il faut alors
  s'arrêter.

### Dépendances

- **Clés étrangères** : aucune référence vers `messages` dans les DDL du
  dépôt. À confirmer avant exécution :
  `SELECT conname FROM pg_constraint WHERE confrelid = 'public.messages'::regclass;`
  Le résultat attendu est vide.
- **Code qui lit `messages`** :
  - quotas (5 chemins) : `status='envoye'` seulement → **non affectés** ;
  - `/api/messages` et le journal admin : l'historique affiche aujourd'hui
    des échecs de juillet ; après le nettoyage, il affichera les envois réels ;
  - `/api/kpis` : `messagesSent` compte **toutes** les lignes, échecs
    compris. Le tenant pilote affiche 38 732 au lieu de ~30. Le filtre
    `status='envoye'` n'est à ajouter **qu'après** 005 ou D3 : sans index, il
    obligerait à lire la table pour 493 k lignes (tenant B).
  - « Tout renvoyer » (page Messages) : il renvoyait ces échecs de juillet.
    C'est corrigé sur la branche `p1-legacy-send-guards`, qui limite aux
    échecs de moins de 24 h.
- **Autre application** : elle utilise `WaMessage`, pas `messages`. La
  répartition par tenant ne montre que des tenants AutoTim.

### Risques du fichier tel qu'écrit

1. **Le gain d'espace annoncé ne se matérialise pas.** `DELETE` puis `VACUUM`
   ordinaire rendent l'espace réutilisable _par la table_, mais ne réduisent
   pas les fichiers. Seules les pages vides **en fin de table** sont
   tronquées. Or les 45 lignes conservées sont dispersées d'avril à juin, et
   les trois index ne rétrécissent pas. Le quota de 500 Mo ne baisserait
   donc que partiellement, alors que l'en-tête promet « ~200 Mo libérés ».
2. **Coût croissant des lots E3.** Chaque `SELECT id … LIMIT 10000` relit le
   tas depuis le début, à travers les tuples morts laissés par les lots
   précédents. Sur ~54 lots, la lecture cumulée se compte en Go sur une
   instance Free déjà sujette à des 504 de passerelle.
3. **Fausse sécurité de l'archive E2.** L'archive vit dans la même base : elle
   _double_ l'espace consommé jusqu'à sa suppression.
4. **Audit.** La suppression efface la trace ligne à ligne de l'incident.

### Stratégie sûre proposée (non appliquée)

Il reste 45 lignes sur 532 516. Il est donc plus sûr de **reconstruire que de
supprimer** :

```sql
-- 0. Hors fenêtre de mesure, heure creuse, sauvegarde manuelle faite
--    (workflow db-backup), plus un export CSV des lignes éligibles conservé
--    hors base (preuve et rollback).
-- 1. Agrégats d'audit conservés (petits) :
CREATE TABLE IF NOT EXISTS autotim.messages_incident_2026_stats AS
SELECT user_id, date_trunc('day', sent_at) AS jour, status, error_message, count(*) AS n
FROM public.messages GROUP BY 1, 2, 3, 4;

-- 2. Reconstruction atomique (verrou exclusif de quelques secondes) :
BEGIN;
LOCK TABLE public.messages IN ACCESS EXCLUSIVE MODE;
CREATE TEMP TABLE keep ON COMMIT DROP AS
  SELECT * FROM public.messages
  WHERE NOT (status = 'echec'
             AND error_message LIKE '%Session WhatsApp expirée%'
             AND sent_at < now() - interval '30 days');
-- Garde-fou : doit valoir 45 (+ lignes postérieures au 2026-09-10 éventuelles)
DO $$ BEGIN
  IF (SELECT count(*) FROM keep) > 1000 THEN RAISE EXCEPTION 'keep inattendu'; END IF;
  IF (SELECT count(*) FROM keep WHERE status = 'envoye')
     <> (SELECT count(*) FROM public.messages WHERE status = 'envoye') THEN
    RAISE EXCEPTION 'envoye perdu';
  END IF;
END $$;
TRUNCATE public.messages;              -- nouveau fichier : espace RENDU immédiatement
INSERT INTO public.messages SELECT * FROM keep;
COMMIT;
ANALYZE public.messages;
```

- **Espace** : `TRUNCATE` libère réellement les ~210 Mo, index compris, sans
  `VACUUM FULL`.
- **Verrou** : quelques secondes, le temps de lire 210 Mo une fois. Les
  écritures concurrentes dans `messages` (envois) **attendent**, elles
  n'échouent pas.
- **Préalables à vérifier** :
  - aucune clé étrangère vers `messages` (requête ci-dessus) ;
  - aucun trigger sur la table : `SELECT tgname FROM pg_trigger WHERE
tgrelid='public.messages'::regclass AND NOT tgisinternal;` ;
  - `id` en `uuid`, donc pas de séquence à recaler.
- **Rollback** : la transaction échoue d'un bloc (garde-fous). Après commit,
  restauration depuis l'export CSV ou la sauvegarde hebdomadaire chiffrée.
- **Impact WhatsApp et campagnes** : nul. Les quotas ne lisent que `envoye`,
  et `campaign_recipients` est une table distincte.
- **Après** : ajouter `status='envoye'` au KPI `messagesSent`. D3 devient
  optionnel.

**Décision requise (propriétaire)** : E2/E3 restent « plus tard ». Cette
stratégie remplace E2/E3 si le nettoyage est validé. Rien n'est exécuté.
